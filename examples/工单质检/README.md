# 样板间 · 客服工单质检

第三个职业模板。同一个引擎、同一份 schema，只把判据内容从「凭证」「错题」换成「工单」。

```bash
python tools/contract_check.py contracts/工单质检.json   # 先体检
python tools/score.py contracts/工单质检.json             # 再打分
```

## 两个数据文件，各管一件事

| 文件 | 是什么 | 谁在用 |
|---|---|---|
| `tickets.json` | 10 条全合规的工单 | 契约的默认路径，跑出来必须是 100 分 |
| `tickets-broken.json` | 7 条故意写坏的工单，**一条只犯一个错** | `tests/benchmark_data.py` 喂给判据，证明七条判据各自会红 |

为什么不是一个文件 5 绿 5 红：本引擎的判据单位是"**一批数据合不合规**"，
不是"给每条记录打分"。一批评判里混进一条坏的，整条判据就该红 —— 那是验收；
"哪条要人去处理"是队列视图，属于样板间的界面，不属于契约。

## 七条判据在守什么

| 判据 | 守的红线 | 坏样本 |
|---|---|---|
| T1-a | 结论要能指到一笔具体订单 | `B-001` 缺 `order_id` |
| T2-a | 对客户的承诺不能随口给 | `B-002` 含「保证退款」 |
| T3-a | 超时是唯一能用时间戳证明的违约 | `B-003` 30 小时才响应 |
| T4-a | 高风险不能留在没处置权的人手里 | `B-004` 高风险无升级路径 |
| T5-a | 例外可以放，但放行的人要留名 | `B-007` 有理由、有时间，就是没签字 |
| T6-a | 机器只填空，不覆盖人工值 | `B-006` 人工改成 996，最终值是 106 |
| T7-a | 同源影子不能给自己当复核 | `B-005` 准备与复核都来自 `proxy:colleague` |

T5 这条原来是个漏洞：坏样本里一张例外记录都没有，于是 T5-a 从加载那天起就没红过 ——
报告上它一直绿，但没人知道它咬不咬得住。补 `B-007`（例外有理由、有时间、没签字）之后才补上。
「判据不能只红不绿」那一面由 `B-data-12` 盯：好样本必须全绿。

## 数据

全部虚构。联系方式一律写成 `demo-contact-00N`，没有真实客户、订单、电话、邮箱。
