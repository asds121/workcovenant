# 仓库治理：让这个仓库用自己的框架管自己

> 一份框架如果连自己的仓库都管不住，它就没有资格管别人的工作。
> 所以这里不是「最佳实践清单」，是**已经跑起来的判据** —— 红了就发不出去。

执行入口：[`contracts/仓库治理.json`](../contracts/仓库治理.json)。
三条命令，任何一条红了都不发布：

```bash
python tools/privacy_scan.py --tree --history        # 无敏感信息
python tools/contract_check.py contracts/*.json       # 契约写全了没有
python tools/score.py contracts/仓库治理.json         # 四条治理维度的总分
```

---

## 1. 四个维度，各自在防什么

| 维度 | 防的是什么 | 代表判据 | 失败长什么样 |
|---|---|---|---|
| **高质量** | 交付了但读不懂、缺文件、占位实现、巨型文件 | G1-a…G1-d | 新人打开仓库，找不到入口；代码里躺着 `TODO` |
| **可信** | 分数不可复现、契约漏验关键动作、质量门自己不及格 | G2-a…G2-c | 同一份契约两次跑出不同分；100 分但关键动作没验 |
| **合规** | 许可不明、归属缺失、贡献/漏洞没有渠道 | G3-a…G3-c | 企业法务判"不可用"；有人报漏洞只能开公开 issue |
| **无敏感信息** | 真实企业名、税号、账号、密钥、本机路径进了工作树或历史 | G4-a…G4-c | 推上去那一刻起，任何人都能 checkout 出来 |

四条里只有**无敏感信息**是"一次失败就不可逆"的，所以它有三条阻断项，
并且从三个角度验：工作树、历史、扫描器自己。

---

## 2. 为什么敏感信息要有三条判据

一条判据只能证明一个角度。三个角度缺一不可：

| 判据 | 证明什么 | 缺了会怎样 |
|---|---|---|
| `G4-a` 工作树 | 现在这份代码是干净的 | 提交前没人拦，靠人肉 review |
| `G4-b` 历史 | **从来**没脏过 | 工作树删干净了，历史里还留着，改工作树毫无意义 |
| `G4-c` 植入测试 | 扫描器真的会红 | 规则写歪了，扫描器变成"永远说干净"的装饰品 |

第三条最容易被跳过，也最贵。一个只会说"干净"的扫描器给的是**假体检报告**：
它比没有扫描器更危险，因为它让人停止怀疑。

所以规则自带正反例（`wvc/privacy.py` 里每条规则的 `hits` / `misses`），
`tools/privacy_scan.py` 每次运行都先跑一遍自测；自测不过直接退出码 3 ——
**"扫描器坏了"和"仓库脏了"必须是两个不同的结论。**

---

## 3. 规则清单（8 条）

| 规则 | 抓什么 | 为什么敏感 |
|---|---|---|
| P1 | 统一社会信用代码 / 税号 | 能直接定位到一家具体企业 |
| P2 | 身份证号 | 个人信息，公开即不可撤回 |
| P3 | 手机号 | 同上 |
| P4 | 邮箱（白名单：GitHub noreply / example / apache） | 客户与同事邮箱不该出现在公开仓库 |
| P5 | 私钥 / GitHub 令牌 / OpenAI 密钥 / AWS key / Slack token | 凭证泄露 = 写权限送人 |
| P6 | 本机绝对路径（盘符接 Users 目录、/home 接家目录） | 泄露机器用户名与目录结构，也让他人跑不通 |
| P7 | 企业主体名（…有限公司 / 事务所 / 研究院） | 账套数据里最硬的身份标识 |
| P8 | 银行账号 | 账号 + 户名 = 一笔可发起的支付指令 |

**报告里一律打码**（前 2 后 2）。否则这份报告本身就是新的泄露源，
而且它一定会被贴进 issue 里。

## 4. 已知局限（写出来，比藏着强）

1. **扫不到图片和 PDF 里的文字。** 本仓库目前只有文本文件，一旦加截图，
   需要先做 OCR 再扫 —— 现在没有，所以这条是空的，不是已覆盖。
2. **二进制与 >2MB 的文件会被跳过**，但会进 `skipped` 清单并打印出来。
   跳过不是"没扫到就算了"，它是可见的。
3. **历史只扫新增行。** 判断依据是"引入过什么"，而不是"删掉过什么"；
   删除行里的敏感串既然已经被后续提交移除，重点在它曾经存在过 —— 这一点已覆盖。
4. **规则是黑名单，不是分类器。** 它防的是已知形态的泄露，不防"用文字描述出来的客户信息"。
   后者只能靠人：`CONTRIBUTING.md` 里写了不许提交什么。
5. **不加白名单后门。** 唯一的"白名单"是规则里的 `allow` 字段（如 GitHub noreply 邮箱），
   它随规则一起被自测盯着；不要因为误报就去改扫描范围 —— 改规则，并给它加反例。

## 5. 发布前 checklist（人 vs 机器）

机器能判的已经在契约里了。剩下这几件只能人做，写在这里免得下次忘：

- [ ] `CHANGELOG.md` 写了这次改了什么、为什么（口径变化必须写）。
- [ ] 如果改了判据语义，`docs/契约规范.md` §7 的升版规则跟上了。
- [ ] 新增的职业契约，`why` 不是凑数的。
- [ ] 没有为了"让它绿"而放宽判据 —— 放宽可以，但要在 PR 里说清理由。

---

## 6. 为什么值得这么麻烦

因为这个仓库的卖点是"验收不靠感觉"。
如果它自己的验收靠感觉，那它卖的就不是框架，是一套说辞。
