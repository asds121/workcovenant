# 评审：《同事契约与四角色加固 v1.1》

> **结论**：机制直觉是对的，**形态不对**。这份稿子写的是一个「变更执行运行时」的验收规范 ——
> 有状态机、有备份、有 trigger、有还原范围；本仓库写的是「一批工作合不合格」的判据框架。
> 整份照搬，等于给一个不存在的系统发合格证，那正是本仓库最恨的假绿。
>
> 所以下面逐条裁决：**采纳 10 条**（其中 3 条进了代码）、**改造采纳 4 条**、
> **部分采纳 3 条**、**已有 4 条**、**不采纳 10 条**。采纳的已经跑起来了，不采纳的写清边界。

---

## 0. 三条尺子

判断一条建议该不该进，只用这三条 —— 它们也是这个仓库自己的立身之本：

1. **形态约束**：零依赖、单文件 JSON、`format` 已冻结（`docs/契约规范.md` §7）。
   要引入解析器、第二份配置、第二套版本号，先问值不值。
2. **真**：判据必须能指到仓库里的真文件、真命令、真数据。**没有运行时，就不写运行时判据** ——
   否则测试的对象是自己的 fixture，绿得再漂亮也只证明 fixture 写得对。
3. **简**：删掉它不会导致判断错误，就删。判据的密度不是美德，判据的**分辨力**才是。

## 2. 采纳的三条机制（以及它们照出了我们什么）

### 2.1 `blocking` 不可被悄悄关掉 —— 原稿只有策略，没有机制

原稿说"blocking 判据不可被禁用，只能升版本移除"。问题是：**怎么知道它被禁用了？**
没有基线，"被禁用"不是一个可观测事件 —— 把 `blocking: true` 改成 `false`，
契约照常加载、照常显示、分数只会变好看。这正是本仓库 §6 塌陷清单里那条
"阻断项变成提醒一下"，之前只能靠人看 diff 拦住。

现在的做法（`wvc/lock.py` + `tools/lock_check.py` + 治理判据 `G5`）：

- 每份契约有一份基线（判据 id + 是否阻断 + **判定内容的指纹**）；
- 同版本下，任何新增/删除/改动 → 红，并列出全部差异；
- 升版本后，删除/降级/改内容 → 放行，但必须是 `CHANGELOG.md` 里点到名的；
- 说明文字（`why` / `title`）不进指纹 —— 改措辞不该逼人升版本。

它做不到的：重新生成锁只要一条命令。**锁不能让放松变得不可能，只能让它变得当众。**
这句话写进了模块 docstring，免得下一个人把它当银弹。

### 2.2 字段名写错不许静默 —— 原稿的"语义必须明确"，照出了我们自己的洞

原稿最硬的一句是"判据执行语义必须明确"。照这句话回头看本仓库，发现一个真的洞：

```text
{"kind": "file", "path": "a.md", "blockng": true}   →  旧校验：通过
```

少一个 `i`，那条判据就**再也不阻断**，而报告里它看起来一切正常。
`validate()` 原来只检查"该有的有没有"，从不检查"多出来的认不认识"。

现在：顶层、需求、判据三层都走白名单，字段还分归属（`run` 只属于 `cmd`，
`assert` 只属于 `data`）。写错的键比没写更吵。基准集补了两条
（`B-contract-08` / `B-contract-09`），反证补了 `M10`。

### 2.3 同源不是独立复核 —— 原稿 R12 照出了协议里一句站不住的话

`docs/四角色协议.md` v0.1 §4 原文：「人没有同事复核，机器当第二双眼睛。」

这句话听着提气，但它悄悄假设了机器是**独立**的。实际上机器和你看的是同一批数据、
同一套判断长出来的 —— 它是**同源代理**。同源代理能替你查算错、查漏字段、查前后不一致，
不能替你判"这个判断对不对"。它会把你的偏差复核成一致，然后告诉你"没问题"。

这三件事一起改：

- 协议新增 §2.5，并改掉 §4 那句话（不是删掉，是补上边界）；
- `data` 判据有了 `compare` 子句：`author_source ≠ reviewer_source`；
- 工单质检 `T7-a` 是它的可执行版本：准备与复核都来自 `proxy:colleague`，判红。

### 2.4 补记：「同事」还有一项学习权（用户指出，原稿漏了）

第一版裁决里我写的是「同事不是第五个角色，权力为零」。这句话只对了一半 ——
**判定权确实为零，但它有学习权**：把一轮工作的漏判与误判，整理成下一版判据。

原稿的 C1–C10 全是判定侧的动作（执行/提交/审核/签字），所以它看起来什么权都没有；
但 §4 那条闭环里「提交的结论反哺机器」缺了一个执行者 —— 谁来把这一轮盘成下一版判据？
没有人的话，复盘永远停在"下次注意"，长不成判据。

于是协议改成两层，而不是简单加一行：

| | 判定权 | 学习权 |
|---|---|---|
| 持有者 | 你 / 经理 / 实习生 / 助理 | 同事（唯一） |
| 作用对象 | 这一条工作 | 判据本身 |
| 产物 | 结论、阻断、补空、解释 | 判据草案（新增 / 收紧 / 放宽） |
| 能不能自己生效 | 判定本来就是终态 | **不能**：人触发 + 升版本 + CHANGELOG + 重新生成锁 |

顺带解决一个撞名：`docs/产品内涵.md` 里"复盘"是助理的活。不拆开，同一个动作就有两个持有者，
违反「权力唯一」。拆法按对象：**助理解释给人听，同事整理成判据草案。**

这也让 §7 的通胀门槛第一次真的用上第二条路 —— 同事不扛 blocking 判据，
但它消掉了一类每周都在做、又永远没人做的事。

## 3. 改造后采纳：第三个职业模板

原稿的样板间是这份文档里唯一能直接落地的东西，但有三处必须改：

**① 5 绿 / 5 红拆成两份文件。** 原稿把好数据和坏数据混在一批，是因为它的模型是
"给每条记录打分"。本引擎的判据单位是"**这一批合不合规**"：混进一条坏的，整条判据就该红。
所以 `tickets.json`（10 条全合规）+ `tickets-broken.json`（6 条，一条只犯一个错），
后者由 `tests/benchmark_data.py` 直接喂给真契约 —— 好样本证明不误伤，坏样本证明咬得住。

**② 11 条判据只留 7 条。** 原稿那 5 条角色加固里，`R6 助理解释权`、`C8 预览留痕`、
`C9 派活合规`、`R4 blocking 不变` 在工单数据里没有载体，硬写只能造字段来喂自己。
留下的是四条业务红线 + 人工值 + 同源 + 例外签字，每条都能指到一条具体记录。

**③ 不做 20 种判据类型，只做 4 个子句。** 原稿的 evaluator 表列了 20 多种 type。
本仓库只加了 `data` 一种 kind 和 `required / forbidden / compare / sla` 四个子句：

| 子句 | 它能判的 | 它替代了原稿里的 |
|---|---|---|
| `required` | 必填字段、条件必填（`when`） | D1、D4、D6、C1 的一部分 |
| `forbidden` | 禁词 | D2 |
| `compare` | 同源 / 人工值（`eq` / `ne`） | D5、R12 |
| `sla` | 两个时间戳的间隔 | D3 |

四个子句覆盖了原稿 6 条业务判据的全部，代价是 60 行执行器 —— 这才叫"机制一个字没改"。

## 4. 不采纳的五处，以及为什么

### 4.1 不引入 YAML / `core.yaml`

零依赖是硬约束：解析 YAML 要装包，装包才能验收的框架，验收本身会先被放弃。
更麻烦的是它会变成第二份"核心清单"—— 与 `docs/四角色协议.md` 并列，两份都会声称自己是真的。

### 4.2 不改退出码

原稿把 `2` 定义成 `runtime_error`。本仓库 `2` 是"没有未过、但有未验"，`3` 是契约坏了。
这不是命名之争：**缺料和程序坏了必须分开**。缺料是"料没到，这条不该判"，
程序坏了是"这次结论一分都不该信"。合并之后，一次 `FileNotFoundError` 会显示成"没验"，
而一次缺料会显示成"引擎坏了" —— 两种都把责任推给了错的人。

原稿对"证据缺失时 blocking 判红"的坚持，出发点是对的（别让缺料变成灰就放过），
但结论下反了：把 `2` 留在流水线里，CI 一样会停（非零），人看到的是"没验完"而不是"验过且不过"。
**红是"验过、不合格"，灰是"没验"** —— 这个区分是这个仓库最不该让掉的东西。

### 4.3 不做 evaluator 类型系统

20 多种 type，每种要一个执行器、一组 fixture、一条反证。而其中大半（`state_separation`、
`backup_integrity`、`restore_scope`、`preview_review_trace`、`dispatch_trace`）需要运行时事件流。
没有事件流，它们只能读 fixture —— 那测试的是 fixture 的作者，不是被验收的系统。

### 4.4 不写没有运行时的判据

C1 / C2 / C3 / C4 / C9 / C10 都在描述"某个动作有没有发生"。本仓库里没有那个动作，
写出来只能是断言 JSON 里的一个字段等于某个值。这类判据有个共同的名字：**自证**。

顺带一句判据密度的问题：C1（不得置 effective）、C2（必须人触发）、C6（禁止 execute / auto_trigger）、
C7（final: human）**四条在说同一件事**。四条全红只能告诉你一件事，报告会长，判断不会更准。
同理，12 条 mutation 里有 4 条注入的都是"执行"，咬住一次就够了。

### 4.5 不做虚构日志与"修完全绿"

`[core] core v1.0 loaded` 那种输出是**描述**，不是证据。本仓库的报告逐条来自判据执行，
证据是"退出码 + 输出片段""文件大小 + 命中行""哪条记录缺哪个字段"。

"修复 #2–#6 后全绿"也不采用：验收回答的是"当前状态合不合格"，不是"你修完给我看"。
后者一写进验收，就会变成"演示通过即交付"。

## 5. 这份稿子没解决、我们也没解决的

1. **锁只能让放松可见，不能让它不可能。** 重新生成基线是一条命令的事 —— 它留下 diff，不设路障。
2. **同源问题在真实系统里只能靠外部证据兜底。** `compare` 子句只能证明"两条来源字段不同"，
   证明不了"复核的人真的独立判断过"。
3. **`data` 只覆盖四类形状。** 它不是规则引擎，第五种子句要等第五个真实职业提出来再加。
4. **"人有没有看过差异"仍然只能靠人留证。** 没有运行时，就没有 `viewed_at`；
   证据三件套只是让人写清楚，不是让机器验证。
5. **原稿的 `evidence_not_inheritable` 我们算天然满足**（每次重跑），但这也意味着
   本仓库无法验收"跨次继承"的场景 —— 没有缓存，就没有继承问题，也就没有这条判据。
