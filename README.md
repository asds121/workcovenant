# WorkCovenant · 职业契约框架

> **一句话**：它不是又一个软件工具，而是一套把「验收」从口头甩锅变成**可执行判据**的开源契约框架 —— 让"软件不折磨人、单人也能带数字团队、约束不是敌人"变成可运行、可验证、可复用的默认期望。

它是一个**框架**，不是产品；会计那个 PDF 分录工作台是它的**样板间**，证明框架能落地，不是框架本身。
样板间可以减功能，不能跑不通。

## 这件事在解决什么

现在的软件验收，常态是这三句：

- 「基本支持了」—— 哪一步断了，没人知道；
- 「验收靠感觉」—— 谁嗓门大谁过；
- 「出事再补」—— 责任在流程里蒸发。

WorkCovenant 只做一件事：**把"做到"写成一段能一口气走完的动作，再用机器判它。**

一条需求必须有三段，少一段就不算数：

| 段 | 是什么 | 反例 |
|---|---|---|
| **原话** | 谁在什么时候说的，逐字 | "用户希望体验好" |
| **最小闭环** | 一段能一口气走完的动作 | "支持拖拽缩放" |
| **判据** | 机器能跑、能说出差在哪 | "应该比较流畅" |

## 四层结构

| 层 | 是什么 | 换一个职业还剩什么 |
|---|---|---|
| **契约框架** | 把工作拆成最小闭环、强要求、状态机、证据链、评分 | **全部** |
| **数字流程经理** | 强约束、交叉核验、状态推进、锁定、留痕、评分 | 机制全留，规则换 |
| **助理 + 机器实习生** | 解释引导 / 抽取补空 | 机制全留，话术换 |
| **样板间** | 某一个职业的具体实现（本项目里是会计） | **全丢** |

判断"这一条该进哪层"只有一个问法：**把会计换成护理排班 / 教培批改 / 工程验收，这句话还成立吗？**
成立 → 框架；不成立 → 样板间。所以框架层里**不许出现科目名、凭证号、账套名**。

## 四角色：单人背后的数字团队

| 角色 | 像什么 | 只有他能做 | **绝不许做** |
|---|---|---|---|
| **你** | 决策者 / 老板 | 定方向、确认结论、最终签字 | 不做重复劳动、不盯流程 |
| **机器实习生** | 下属 | 抽取、补空、批量核对 | **不覆盖人工值**、不做审核 |
| **数字流程经理** | 流程主管 | 拦错、锁定、留痕、评分 | **不做业务判断**、不替人决策 |
| **助理呈现层** | 好上司 / 教练 | 解释、提醒、引导、复盘 | **不命令**、不训导、不替人拍板 |

一句能记住的分工：**实习生补空，经理拦错，助理解释，你签字。**

精髓不在"分工"，在**人机互训**：你提交的结论反哺机器，机器再把空补回来 ——
用户既被"好上司"带，又在管理"机器实习生"。管理岗的经验就是这么长出来的。

细节与每个角色的落地判据见 [`docs/四角色协议.md`](docs/四角色协议.md)。

## 契约长什么样

一份契约就是一个 JSON 文件（schema `workcovenant.contract/1`）：

```json
{
  "format": "workcovenant.contract/1",
  "id": "training-ability",
  "name": "教培能力契约",
  "profession": "教培（批改与认证）",
  "version": "1.0.0",
  "owner": "契约设计者",
  "requirements": [
    {
      "id": "L2",
      "title": "认证不能自己给自己签",
      "verbatim": "教师从讲授者变成契约设计者 + 证据审核者 + 教练。",
      "loop": ["学习者提交认证申请", "审核者签字", "签字的人必须不是学习者本人"],
      "criteria": [
        {
          "id": "L2-b",
          "title": "签字人 ≠ 学习者",
          "why": "自证一放开，所有证据立刻失去意义",
          "kind": "cmd",
          "blocking": true,
          "run": "{python} -c \"...\"",
          "expect": { "stdout_contains": "OK" }
        }
      ]
    }
  ]
}
```

判据只有四种可执行形态（`cmd` / `file` / `links` / `manual`），全字段说明见
[`docs/契约规范.md`](docs/契约规范.md)。

**`why` 是必填的** —— 每条判据都要说清守的是哪根红线。写不出 `why` 的判据，
就是"为了测而测"，它只会消耗维护成本，不会拦住任何东西。

## 分数怎么算

- 每条需求得分 = 通过判据数 ÷ 判据总数。
- **`—`（没验）进分母、不进分子** —— 缺料、没留证据，一律不算过。
- 总分 = 各需求得分的平均（需求之间等权）。
- **阻断项一票否决**：任何 `blocking` 判据红了，结论直接"不通过"，但**分数照常显示** ——
  既不许把分数抹成 0（那会掩盖别的进展），也不许让分数把它盖过去。
- 退出码：`0` 全过 / `1` 有未过 / `2` 只有未验 / `3` 契约本身坏了。

**分数低不可怕，分数假才可怕。** 低分只是"还没做"；假分数会把下一轮时间全浪费在已经坏掉的地方。

### 为什么还要一个反证脚本

一个永远报绿的引擎，比没有引擎更能骗人。`tools/mutation_check.py` 故意把东西改坏六次
（改期望、删交付物、缺前置料、阻断项红、人工项没证据、契约缺字段），**每一次都必须当场变红**。
改不红就说明那一类错误会静默漏过去。

## 这个仓库里有什么 / 没有什么

**有**（框架层，全部可跑）：

- 契约 schema v1.0 + 加载与全量校验（[`wvc/contract.py`](wvc/contract.py)）
- 判据执行器：三档结果、缺料不算过、交付物缺失算红（[`wvc/checks.py`](wvc/checks.py)）
- 打分与报告（[`wvc/score.py`](wvc/score.py)）
- 两份**真跑**的契约：[`contracts/仓库交付.json`](contracts/仓库交付.json)（对本仓库自己打分）、
  [`contracts/教培-能力契约.json`](contracts/教培-能力契约.json)（证明可迁移）
- 反证脚本与回归钉子（[`tools/mutation_check.py`](tools/mutation_check.py)、[`tests/`](tests/)）
- 核心文档原文：[`docs/产品内涵.md`](docs/产品内涵.md)（讨论过程，不改）

**没有**（刻意不发）：

- **会计样板间的源码**。它含真实客户的账务数据与私有素材，不进公开仓库。
  它的契约原文（R1–R8 + 三个「适」）在 [`docs/样板间-会计.md`](docs/样板间-会计.md)，
  你能看到"要求长什么样"，但那份实现不在树里 —— 所以它的判据在本仓库里跑不出分，
  这是**诚实的空缺**，不是被藏起来的绿。
- 任何 UI 框架依赖。这一层是纯标准库；界面属于各个样板间。
