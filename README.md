# WorkCovenant · 职业契约框架

[![verify](https://github.com/asds121/workcovenant/actions/workflows/verify.yml/badge.svg)](https://github.com/asds121/workcovenant/actions/workflows/verify.yml)

> **一句话**：它不是又一个软件工具，而是一套把「验收」从口头甩锅变成**可执行判据**的开源契约框架 —— 让"软件不折磨人、单人也能带数字团队、约束不是敌人"变成可运行、可验证、可复用的默认期望。

它是一个**框架**，不是产品；会计那个 PDF 分录工作台是它的**样板间**，证明框架能落地，不是框架本身。
样板间可以减功能，不能跑不通。

---

## 一分钟

零依赖（只要 Python 3.10+，不装任何包），克隆下来直接跑 —— 本机实测 48 秒
（Windows / Python 3.12，四份契约连锁打分），七条命令全跑约 90 秒。

```bash
git clone https://github.com/asds121/workcovenant.git
cd workcovenant

python tools/score.py contracts/仓库交付.json
```

**预期输出**（这就是"可验证"的样子，不是"应该能跑"）：

```text
WorkCovenant 契约打分 · 仓库交付契约 1.2.1 · 通用（开源仓库）
4 条需求 · 15 条判据 · 15 过 / 0 没过 / 0 没验
==============================================================================
R1   一眼知道这是什么　3/3　做到
   ✅ 阻断·R1-a     README 在，且不是占位文件
              README.md 16.6 KB
...
按需求：R1 100%　R2 100%　R3 100%　S1 100%
总分 100 / 100
结论：通过
```

第一次来、想先看懂"判据长什么样"：去 [`examples/最小契约/`](examples/最小契约/) ——
三条判据、三张单子、七十一行契约，把 `128.00` 改成 `128.10` 就红给你看。

七条命令，七种"不体面"都能当场暴露：

```bash
python tools/contract_check.py contracts/*.json   # 契约自己写全了没有
python tools/benchmark.py                         # 57 种失败模式，引擎还认不认得出来
python tools/coverage_check.py                    # 哪几条阻断判据从来没被弄红过
python tools/mutation_check.py                    # 引擎咬不咬得住（10 条反证）
python tools/lock_check.py --check                # 门槛有没有被悄悄调松
python tools/privacy_scan.py --tree --history     # 有没有敏感信息（含历史）
python -m unittest discover -s tests -t . -q      # 判定口径的回归钉子
```

> **契约体检绿 ≠ 验收通过。** `contract_check` 绿，只说明这份契约能加载、字段没写错；
> `score` 绿，才说明这批工作合格。前者是"装得对"，后者是"做得对" ——
> 混成一句，就会拿"契约没毛病"去替"活没干好"背书。

换一个职业，看第二份契约（判据内容全换，机制一个字没改）：

```bash
python tools/score.py contracts/教培-能力契约.json
```

换一种数据结构 —— 不是文件，是一批记录：

```bash
python tools/score.py contracts/工单质检.json       # 7 条 data 判据，规则写在契约里
```

## 这件事在解决什么

现在的软件验收，常态是这三句：

- 「基本支持了」—— 哪一步断了，没人知道；
- 「验收靠感觉」—— 谁嗓门大谁过；
- 「出事再补」—— 责任在流程里蒸发。

WorkCovenant 只做一件事：**把"做到"写成一段能一口气走完的动作，再用机器判它。**

一条需求必须有三段，少一段就不算数：

| 段 | 是什么 | 反例 |
|---|---|---|
| **原话** | 谁在什么时候说的，逐字 | "用户希望体验好" |
| **最小闭环** | 一段能一口气走完的动作 | "支持拖拽缩放" |
| **判据** | 机器能跑、能说出差在哪 | "应该比较流畅" |

## 四层结构

| 层 | 是什么 | 换一个职业还剩什么 |
|---|---|---|
| **契约框架** | 把工作拆成最小闭环、强要求、状态机、证据链、评分 | **全部** |
| **数字流程经理** | 强约束、交叉核验、状态推进、锁定、留痕、评分 | 机制全留，规则换 |
| **助理 + 机器实习生** | 解释引导 / 抽取补空 | 机制全留，话术换 |
| **样板间** | 某一个职业的具体实现（本项目里是会计） | **全丢** |

判断"这一条该进哪层"只有一个问法：**把会计换成护理排班 / 教培批改 / 工程验收，这句话还成立吗？**
成立 → 框架；不成立 → 样板间。所以框架层里**不许出现科目名、凭证号、账套名**。

## 四角色 + 一个学习角色：单人背后的数字团队

| 角色 | 像什么 | 只有他能做 | **绝不许做** |
|---|---|---|---|
| **你** | 决策者 / 老板 | 定方向、确认结论、最终签字 | 不做重复劳动、不盯流程 |
| **机器实习生** | 下属 | 抽取、补空、批量核对 | **不覆盖人工值**、不做审核 |
| **数字流程经理** | 流程主管 | 拦错、锁定、留痕、评分 | **不做业务判断**、不替人决策 |
| **助理呈现层** | 好上司 / 教练 | 解释、提醒、引导、对人复盘 | **不命令**、不训导、不替人拍板 |

一句能记住的分工：**实习生补空，经理拦错，助理解释，你签字。**

**再加一个只学习、不判定的角色：同事。** 它把每一轮的漏判与误判，盘成下一版判据草案 ——
这叫学习权，只有它有。它不签、不否、不填、不解释，所以不进上面那张判定表；
而草案也不能自己生效：要人触发、升版本、写 CHANGELOG，否则它就绕过了锁
（[`docs/四角色协议.md`](docs/四角色协议.md) §1.2）。判定权四档，学习权一档 —— 这就是"四"和"五"不矛盾的地方。

还有一句不那么好听的：**机器是你的同源代理，不是第二双眼睛。**
它和你读同一批数据、用同一套判断长出来 —— 能替你查算错、查漏字段、查前后不一致，
不能替你判"这个判断对不对"。关键决策要有非同源复核；没有，就在记录上写明
"这里没有人复核过"，而不是假装复核过了（[`docs/四角色协议.md`](docs/四角色协议.md) §2.5）。

精髓不在"分工"，在**人机互训**：你提交的结论反哺机器，机器再把空补回来 ——
用户既被"好上司"带，又在管理"机器实习生"。管理岗的经验就是这么长出来的。

细节与每个角色的落地判据见 [`docs/四角色协议.md`](docs/四角色协议.md)。

## 契约长什么样

一份契约就是一个 JSON 文件（schema `workcovenant.contract/1`）：

```json
{
  "format": "workcovenant.contract/1",
  "id": "training-ability",
  "name": "教培能力契约",
  "profession": "教培（批改与认证）",
  "version": "1.0.0",
  "owner": "契约设计者",
  "requirements": [
    {
      "id": "L2",
      "title": "认证不能自己给自己签",
      "verbatim": "教师从讲授者变成契约设计者 + 证据审核者 + 教练。",
      "loop": ["学习者提交认证申请", "审核者签字", "签字的人必须不是学习者本人"],
      "criteria": [
        {
          "id": "L2-b",
          "title": "签字人 ≠ 学习者",
          "why": "自证一放开，所有证据立刻失去意义",
          "kind": "cmd",
          "blocking": true,
          "run": "{python} -c \"...\"",
          "expect": { "stdout_contains": "OK" }
        }
      ]
    }
  ]
}
```

判据有五种可执行形态（`cmd` / `file` / `links` / `manual` / `data`），全字段说明见
[`docs/契约规范.md`](docs/契约规范.md)。

`data` 那一种是给"一批记录"用的：规则写在契约里，看得见，不藏在脚本里 ——

```json
{
  "id": "T7-a",
  "title": "有 reviewed_by 时 author_source ≠ reviewer_source",
  "why": "同一份数据训练出来的影子给自己复核，只会把错误复核成一致",
  "kind": "data",
  "path": "examples/工单质检/tickets.json",
  "assert": [
    { "when": { "field": "reviewed_by", "nonempty": true },
      "compare": { "pairs": [["author_source", "reviewer_source"]], "expect": "ne" } }
  ],
  "blocking": true
}
```

**`why` 是必填的** —— 每条判据都要说清守的是哪根红线。写不出 `why` 的判据，
就是"为了测而测"，它只会消耗维护成本，不会拦住任何东西。

## 分数怎么算

- 每条需求得分 = 通过判据数 ÷ 判据总数。
- **`—`（没验）进分母、不进分子** —— 缺料、没留证据，一律不算过。
- 总分 = 各需求得分的平均（需求之间等权）。
- **阻断项一票否决**：任何 `blocking` 判据红了，结论直接"不通过"，但**分数照常显示** ——
  既不许把分数抹成 0（那会掩盖别的进展），也不许让分数把它盖过去。
- 退出码：`0` 全过 / `1` 有未过 / `2` 只有未验 / `3` 契约本身坏了。

**分数低不可怕，分数假才可怕。** 低分只是"还没做"；假分数会把下一轮时间全浪费在已经坏掉的地方。

### 为什么还要一个反证脚本

一个永远报绿的引擎，比没有引擎更能骗人。`tools/mutation_check.py` 故意把东西改坏 10 次
（改期望、删交付物、缺前置料、阻断项红、人工项没证据、契约缺字段、规则改瞎、植入密钥），
**每一次都必须当场变红**。改不红就说明那一类错误会静默漏过去。

### 基准集：失败模式有目录

反证证明"引擎会红"，基准集证明"**红得对**"。`tools/benchmark.py` 是 57 条失败模式，
每条都写死期望结果，按四类判据分组：

| 组 | 覆盖什么 |
|---|---|
| `cmd` | 非零退出码、输出不含、命令不存在、**超时**、GBK 输出、stderr、CRLF |
| `file` | 不在（红不是灰）、空壳、`^$` 锚点、**CRLF 文件**、GBK 文件 |
| `links` | 断链、带标题、尖括号空格、`%20` 编码、代码块里的示例、引用式定义 |
| `manual` | ✅ / ❌ / 没证据 / 有文件没结论 / BOM |
| `contract` | 缺 `why`、id 重复、阻断靠留证、**绝对路径**、`..` 逃逸、`timeout` 越界 |
| `score` | 需求等权、退出码 0/1/2、阻断一票否决、红优先于灰 |

这些用例不是抄现状：`tests/test_benchmark.py::TestLoadBearing` 会把对应修复摘掉，
确认那条用例**真的会红** —— 一条永远绿的用例，只是把现状重复了一遍。

## 这个仓库怎么管自己

**这个框架的第一个用户是这个仓库自己。** 一份连自己都管不住的框架，没有资格管别人的工作。

治理契约 [`contracts/仓库治理.json`](contracts/仓库治理.json) 盯五件事，任一不过就不发布：

| 维度 | 防的是什么 | 怎么判 |
|---|---|---|
| **高质量** | 缺文件、占位实现、巨型文件 | 八份必交文件齐全且够长 · 代码里没有 `TODO`/`NotImplemented` · 单文件 py ≤20KB |
| **可信** | 分数不可复现、契约漏验、质量门自己不及格 | 同一契约两次跑**判定逐格相同** · 五份契约全过体检 · 交付契约本身 100 分 |
| **合规** | 许可不明、归属缺失、没有贡献/漏洞渠道 | LICENSE 是 Apache-2.0 全文 · NOTICE 写明归属 · CONTRIBUTING 给了验收命令 |
| **无敏感信息** | 客户名、税号、账号、密钥、本机路径 | 工作树 0 命中 · **git 历史 0 命中** · 植入假密钥必须被抓住 |
| **门槛不变形** | 阻断被悄悄降级、字段名写错导致判据静默失效 | 五份契约与锁一致 · 降级必须升版本并写 CHANGELOG · `blockng` 写错直接拒绝加载 |

```bash
python tools/score.py contracts/仓库治理.json     # 发布前的门
```

关于第三行多说一句：**工作树删干净没用，历史删不干净。** 所以敏感信息扫描有三条判据 ——
工作树、历史、以及"扫描器自己会不会失灵"（规则自带正例与反例，自测不过就退出码 3，
`3` 表示扫描器坏了，这时"干净"两个字毫无意义）。

第五行是后加的，起因写在 [`docs/评审-同事契约v1.1.md`](docs/评审-同事契约v1.1.md) §2.1：
**把 `blocking` 改成 `false`，不会有任何判据变红，只会让报告变好看。**
所以每份契约带一份基线（`contracts/locks/`），同版本下改任何一条判据都红；
升版本可以改，但删掉或降级的判据必须在 CHANGELOG 里点到名。

细节、威胁模型与已知局限见 [`docs/仓库治理.md`](docs/仓库治理.md)。

## 这个仓库里有什么 / 没有什么

**有**（框架层，全部可跑）：

- 契约 schema v1.0 + 加载与全量校验：三层字段白名单、绝对路径拒绝（[`wvc/contract.py`](wvc/contract.py)）
- 判据执行器：五种形态、三档结果、缺料不算过、交付物缺失算红（[`wvc/checks.py`](wvc/checks.py)）
- 打分与报告（[`wvc/score.py`](wvc/score.py)）
- 锁：判定指纹 + 基线校验，阻断不许被悄悄降级（[`wvc/lock.py`](wvc/lock.py)、
  [`tools/lock_check.py`](tools/lock_check.py)）
- 敏感信息扫描器：8 条规则，每条自带正反例，支持扫 git 历史（[`wvc/privacy.py`](wvc/privacy.py)）
- 五份**真跑**的契约：[`contracts/仓库交付.json`](contracts/仓库交付.json)（质量门）、
  [`contracts/仓库治理.json`](contracts/仓库治理.json)（发布门）、
  [`contracts/教培-能力契约.json`](contracts/教培-能力契约.json)（换职业）、
  [`contracts/工单质检.json`](contracts/工单质检.json)（换数据结构：一批记录）、
  [`contracts/工程验收.json`](contracts/工程验收.json)（再换一个职业：复验人 / 照片 / 检测报告）
- 反证脚本（10 条）、基准集（57 条失败模式）、可重放校验、回归钉子（[`tools/`](tools/)、[`tests/`](tests/)）
- 合规文件：[`LICENSE`](LICENSE)、[`NOTICE`](NOTICE)、[`CONTRIBUTING.md`](CONTRIBUTING.md)、
  [`SECURITY.md`](SECURITY.md)、[`CHANGELOG.md`](CHANGELOG.md)
- 核心文档原文：[`docs/产品内涵.md`](docs/产品内涵.md)（讨论过程，不改）

**没有**（刻意不发）：

- **会计样板间的源码**。它进不进公开仓库，是那份仓库主人的决定 —— 框架不替他决定。
  [`docs/样板间-会计.md`](docs/样板间-会计.md) 里放的是 **2026-10-20 的契约快照**
  （R1–R8 / 29 条；现行版已是 19 条需求 / 72 条判据），你能看到"要求长什么样"，
  但那份实现不在树里 —— 所以它的判据在本仓库里跑不出分，
  这是**诚实的空缺**，不是被藏起来的绿。为什么只放快照：同一份真源不该有两个副本，
  抄过来就会漂（这一页就是证据：抄的是 29 条，实际早就是 72 条了）。
- 任何 UI 框架依赖。这一层是纯标准库；界面属于各个样板间。
